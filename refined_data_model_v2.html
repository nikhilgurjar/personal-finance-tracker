How users link to lookup tables
instruments → FK Stores platformId and providerId as FKs. Renaming "Groww" in the lookup table fixes every instrument that references it. The user just picks from a dropdown — no free-text entry for these fields.
User contribution write-once If a user types a platform not in the list, it's written to platforms with isActive: false and queued for review. Other users see it only after approval. Prevents "Growww" vs "Groww" duplicates.
Instruments split into two shapes: fixed-return (FD, RD, PPF, bonds — known rate + maturity) and market-linked (MF, stocks, ETF, NPS — units × NAV, no fixed return). The base fields are shared; subtype-specific fields are stored in an embedded details object so queries on the base fields still work without schema changes.

SIP is not a new table. It reuses schedules with an instrumentId in the template. When the schedule fires it creates two things: a transaction (money movement) and an InstrumentEvent (units credited). The sipScheduleId FK on the instrument points back to the schedule driving it.

What happens when the schedule fires
Step 1 create → A transactions record is created: debit HDFC savings, credit investment account, scheduleId set, instrumentId set.
Step 2 append → An InstrumentEvent of type sip is appended to instruments.events[]: amount=5000, units computed from that day's NAV, transactionId linked back.
Step 3 update → instrument.units += new units, avgCostBasis recomputed as running weighted average. currentValue stays as units × currentNAV — updated separately by NAV sync job.
Step 4 advance → schedules.nextRunAt advanced by rrule. schedules.lastRunAt set. The schedule suggestion system picks it up for next month automatically.
SIP mode: auto vs manual
auto — schedule fires and creates transaction + instrument event without approval. Suitable for bank-mandate SIPs where money moves automatically.
manual — schedule surfaces as a suggestion on the dashboard. User approves after confirming the bank debit happened. Suitable for manual investments where they decide each time.

RD works identically — it's a fixed_return instrument with type rd, principal grows by the installment amount each month, and maturity amount is deterministic.

For Indian users, 99%+ of transactions are in INR. Storing currency: "INR" on every single document is redundant and adds noise. The strategy: store currency only as an explicit override when it differs from the user's base currency.
Currency inheritance model
user_settings root baseCurrency: "INR" — the authoritative default. All reads resolve currency as: doc.currency ?? user.baseCurrency. This single change cuts storage and makes INR implicit everywhere.
accounts inherit / override HDFC savings account = no currency field → implicitly INR. A foreign currency account (USD NRE account) sets currency: "USD" explicitly. This is the only level where override makes structural sense.
transactions inherit from account A transaction's currency is inherited from its debitAccountId's currency. Only store currency on a transaction when it differs from the account (e.g. a USD payment from an INR card — stores exchange rate too).
instruments inherit / override Most instruments are INR. A US stock or international MF sets currency: "USD". currentValueInr is a computed field using a stored exchange rate snapshot.

UPI as a payment method, not an account type
UPI is not an account — it's a payment rail. A UPI payment debits a linked bank account. Model it as transactions.paymentMethod = "upi" with transactions.upiRefId for reconciliation. The underlying account (HDFC savings) is still the debitAccountId. This avoids the common mistake of creating a "UPI account" that doesn't have a balance.

Similarly, credit card spending debits the credit card account (liability), not the bank account. The bank account is only debited when the card bill is paid (that's a separate transfer transaction).
Dashboard currency display
When computing totals (net worth, portfolio value), always reduce to baseCurrency. For Indian users this means: sum instruments in INR directly, convert foreign instruments using their stored exchangeRate snapshot (updated by background job). Never rely on a live FX call for display-time calculations — store the converted value at write time.

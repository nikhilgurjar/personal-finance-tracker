Relationships
transactions → accounts (×2) debitAccountId and creditAccountId — every transaction moves value between two accounts. Replaces the implicit income/expense account type magic.
loan repayment IS a transaction A repayment sets loanId on a regular transactions record. No separate loanRepayments collection. Outstanding balance is computed by summing transactions.amount WHERE loanId = X.
loans → people (1:1) Always linked by personId (FK), never by personName string. The people record is the single source of truth for the person's name.
instruments → accounts (opt) linkedAccountId points to the bank account where the instrument lives. Withdrawals/closures also create a transactions record with instrumentId set.
goals → instruments / accounts ([]) instrumentIds[] and accountIds[] drive currentAmount computation. No embedded allocations array needed — the references are the allocation.
budgets → categories (1:1) categoryId FK instead of a category name string. Renaming a category now propagates correctly.
schedules → transactions (1:N) When a schedule fires it creates a transactions record with scheduleId set. Querying "all transactions from schedule X" is a single indexed query.
categories → categories (self) parentId enables a two-level hierarchy: e.g. Food → Dining Out, Groceries. Analytics can roll up to the parent level.
Firestore collection layout
All entities are root collections under the user path — not subcollections. This allows collection group queries across all users for admin analytics, and avoids deep nesting that complicates security rules and migrations.

Path pattern: /users/{userId}/{collection}/{docId}

Required composite indexes: (userId, date) on transactions · (userId, status, nextRunAt) on schedules · (userId, period, categoryId) on budgets · (userId, personId, status) on loans · (userId, entity, at) on audit_log
